01 · Fondasi

Konsep dasar database

Sebelum bicara offline atau cloud, semua database berangkat dari struktur yang sama: tabel yang tersusun dari baris dan kolom, dengan kunci yang menghubungkan satu tabel ke tabel lain. Arahkan kursor ke tiap baris untuk melihat elemen-elemennya.

▤Tabel

Wadah data yang tersusun rapi seperti spreadsheet: setiap tabel mewakili satu entitas, misalnya petugas atau wilayah.

↔Field (Kolom)

Atribut dari entitas tersebut — nama, status. Setiap kolom punya tipe data tetap (teks, angka, tanggal).

≡Record (Baris)

Satu baris = satu entri data nyata, misalnya data satu petugas lapangan tertentu.

🔑Primary & Foreign Key

PK — identitas unik tiap baris. FK — penghubung ke tabel lain.

02 · Klasifikasi

Jenis-jenis database

Secara garis besar, database terbagi menjadi relasional (SQL) dan non-relasional (NoSQL). Keduanya bisa dijalankan secara offline maupun di cloud — pilihannya bergantung pada bentuk data dan kebutuhan aplikasi.

▦Relasional (SQL)

Data disimpan dalam tabel-tabel yang saling berelasi lewat key. Cocok untuk data terstruktur dan konsisten seperti data administrasi, transaksi, dan sensus.

Contoh: MySQL, PostgreSQL, SQL Server, Oracle

⌘Non-Relasional (NoSQL)

Data disimpan lebih fleksibel: dokumen JSON, pasangan key-value, graf, atau kolom lebar. Cocok untuk data yang bentuknya berubah-ubah atau volumenya sangat besar.

Contoh: MongoDB, Firebase Firestore, Redis, Cassandra

Document

Data sebagai dokumen JSON/BSON, fleksibel per entri. MongoDB

Key–Value

Penyimpanan sangat cepat berbasis pasangan kunci-nilai. Redis

Column-family

Optimal untuk data besar berkolom banyak. Cassandra, BigTable

Graph

Fokus pada relasi antar-node, misal jejaring sosial. Neo4j

04 · Arsitektur Lokal

Database offline

Database offline berjalan di server atau komputer yang berada secara fisik di lingkungan kita sendiri — misalnya di kantor. Semua proses penyimpanan dan pemrosesan data terjadi di perangkat keras yang kita kelola sendiri.

Contoh perangkat lunak: MySQL, PostgreSQL, SQLite, Microsoft SQL Server, Oracle Database — diinstal langsung di server/komputer.

Kelebihan
  • Kendali penuh atas perangkat keras dan data
  • Tidak bergantung pada koneksi internet
  • Tanpa biaya langganan bulanan
  • Latensi rendah untuk akses di jaringan lokal
Kekurangan
  • Perlu keahlian teknis untuk instalasi & pemeliharaan
  • Skalabilitas terbatas oleh kapasitas perangkat
  • Risiko kehilangan data jika tidak ada backup fisik
  • Akses jarak jauh lebih rumit diatur
05 · Arsitektur Awan

Database cloud

Database cloud dikelola oleh penyedia layanan (AWS, Google Cloud, Microsoft Azure, Supabase, Firebase) dan diakses melalui internet. Infrastrukturnya tersebar di data center yang dikelola penyedia, bukan di kantor kita sendiri.

07 · Keandalan Data

ACID & transaksi

Transaksi database — misalnya memperbarui status hasil survei — harus aman meski terjadi gangguan di tengah proses. Empat prinsip ACID menjaga hal ini. Klik tiap kartu untuk melihat contohnya.

A
Atomicity
klik →

Transaksi berjalan utuh atau batal sepenuhnya, tidak ada kondisi setengah jalan.

Contoh: gagal simpan → data tidak berubah sama sekali
C
Consistency
klik →

Data selalu berpindah dari satu keadaan valid ke keadaan valid lain, sesuai aturan yang ditetapkan.

Contoh: total responden tak pernah minus
I
Isolation
klik →

Transaksi yang berjalan bersamaan tidak saling mengganggu satu sama lain.

Contoh: dua petugas update baris berbeda, tak bentrok
D
Durability
klik →

Setelah transaksi disimpan (commit), data tetap aman meski server mati mendadak.

Contoh: listrik padam, data tetap tersimpan

10 · Perlindungan Data

Keamanan & backup

Baik offline maupun cloud, data hanya berharga jika aman dan bisa dipulihkan saat terjadi masalah.

🔒Enkripsi

Lindungi data saat disimpan (at rest) dan saat berpindah (in transit) lewat HTTPS/SSL, terutama untuk data cloud yang melewati internet.

🛂Kontrol akses

Berikan hak akses berjenjang — admin, editor, pembaca — agar setiap pengguna hanya menyentuh data yang relevan dengan perannya.

🗂️Aturan backup 3-2-1

Simpan minimal 3 salinan data, di 2 jenis media berbeda, dengan 1 salinan di lokasi terpisah — kombinasi backup lokal dan cloud paling ideal.

📝Audit log

Catat siapa mengubah apa dan kapan, agar kesalahan atau anomali data dapat ditelusuri kembali.

11 · Pertumbuhan Sistem

Menambah modul baru tanpa merusak database awal

Database jarang selesai sekali jadi. Cepat atau lambat akan ada kebutuhan modul baru — misalnya modul verifikasi lapangan. Triknya: pilih perubahan yang aditif (menambah), bukan destruktif (mengubah/menghapus struktur lama).

Jenis perubahanAman (aditif)Berisiko (destruktif)
KolomTambah kolom baru dengan nilai defaultMenghapus / mengganti tipe kolom lama
TabelMembuat tabel baru yang terhubung via FKMengubah struktur tabel yang sudah dipakai aplikasi lain
LaporanMembuat VIEW baru di atas tabel yang adaMenulis ulang query langsung ke tabel produksi
ConstraintMenambah index baru untuk mempercepat queryMengubah primary key yang sudah dirujuk tabel lain

Contoh kasus: kantor ingin menambahkan modul verifikasi lapangan agar supervisor bisa mengecek ulang hasil entri petugas — tanpa mengganggu tabel petugas dan hasil_survei yang sudah berjalan.

migrasi_modul_verifikasi.sql
-- 1) Tambah kolom baru, aman untuk data lama ALTER TABLE hasil_survei ADD COLUMN status_verifikasi VARCHAR(20) DEFAULT 'Belum Diverifikasi';
-- 2) Tabel baru untuk modul, terhubung lewat FK CREATE TABLE verifikasi_lapangan ( id_verifikasi SERIAL PRIMARY KEY, id_hasil INT REFERENCES hasil_survei(id_hasil), id_supervisor INT REFERENCES petugas(id_petugas), catatan TEXT, tanggal_cek DATE DEFAULT CURRENT_DATE );
-- 3) View laporan gabungan, tabel asli tak tersentuh CREATE VIEW v_progres_verifikasi AS SELECT h.id_hasil, p.nama AS petugas, h.status_verifikasi FROM hasil_survei h JOIN petugas p ON h.id_petugas = p.id_petugas;

➕Additive column

Kolom baru diberi nilai DEFAULT sehingga baris lama otomatis terisi — aplikasi lama yang belum tahu kolom ini tetap berjalan normal.

🧩Tabel modul terpisah

Modul baru punya tabelnya sendiri, hanya "menempel" lewat foreign key — tidak menyentuh struktur tabel inti sama sekali.

🪟VIEW untuk laporan

VIEW adalah "jendela" query tersimpan; membuatnya tidak mengubah data asli, dan bisa dihapus kapan saja tanpa risiko.

12 · Konteks Nyata

Studi kasus: pendataan lapangan

Ilustrasi bagaimana offline dan cloud bisa dipakai bersamaan dalam satu alur kerja pendataan berskala besar.

01

Input data di lapangan

Petugas mencatat hasil kunjungan lewat aplikasi mobile, kadang tanpa sinyal — data tersimpan sementara secara offline di perangkat.

02

Sinkronisasi ke cloud

Saat perangkat kembali online, data otomatis terkirim ke database cloud terpusat sehingga tim di kantor bisa memantau progres secara real-time.

03

Dashboard pemantauan

Data diagregasi menjadi tabel progres per wilayah dan ditampilkan di dashboard web, membantu identifikasi wilayah yang tertinggal.

04

Arsip lokal untuk cadangan

Salinan data tetap diunduh secara berkala ke server kantor sebagai arsip offline, menjaga ketersediaan data meski akses internet terganggu.
